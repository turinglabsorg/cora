# cora — agent notes

Always-on Discord agents with personalities, layered memory, routines and their own Docker desktops. See `README.md` for the architecture and `DESIGN.md` for the panel's design system (read it before any UI change).

## Layout

- `src/main.js` wires everything; `startCora(overrides)` is what the tests start.
- `src/discord.js` persistent Gateway (heartbeat, resume, reconnect) + REST + per-channel `cora` webhooks; the same class runs each agent's own bot (presence-only intents, `say`, `syncProfile`).
- `src/agent-bots.js` one connection per agent with a `CORA_BOT_<NAME>` token: posting, typing, mentions and profile sync as that agent. **Listening is shared**: a bot whose app has Message Content is switched to `LISTENING_INTENTS` (`useIntents`) and its channel messages go to `onGuild` → `Orchestrator.onMessage`, so a private channel is heard as long as one agent's bot is in it; repeats are dropped by message id (`state.seen` / `store.hasMessage`). A bot whose app lacks it asks Discord for the limited intent itself (`PATCH /applications/@me`, flag `1<<19`, granted to apps under 100 servers) and keeps `DIRECT_MESSAGE_INTENTS` (DMs only) until it has it. `AgentBots.fetchMessages` reads history with a bot that can see the channel when the main one gets 403.
- `src/slack.js` the Web API (form-encoded, 429 with `Retry-After`, markdown turned into mrkdwn) and Socket Mode (`apps.connections.open` → WebSocket, every envelope acknowledged before it is handled, `disconnect` reopens) of one Slack app; files go through `files.getUploadURLExternal`/`completeUploadExternal`, and `typing()` is a no-op because Slack has none for bot users. `src/slack-bots.js` one app per agent (`CORA_SK_BOT_<NAME>` + `CORA_SK_APP_<NAME>`), each on its own socket: channel messages reach `Orchestrator.onSlackMessage`, `message.im` reaches `onSlackDirect`, and the panel generates the app manifest because Slack takes a bot's name from its app, not from the API.
- `src/channels.js` where the cora lives: Discord, Telegram or Slack (`settings.transport`), one at a time, plus the panel rooms; `info(id)` gives prompts the `where`/`place` of a channel. Telegram channel ids are `tg:<chat id>`, Slack ones `sl:<channel>` and `sl:<channel>:<thread ts>` for a thread; `transportOf(id)` is the single rule that says which transport an id belongs to.
- `src/telegram.js` Bot API client (getUpdates long polling, HTML messages, files); `src/telegram-bots.js` agents' own Telegram bots (`CORA_TG_BOT_<NAME>`, send only).
- `src/secrets.js` writes a token pasted in the panel into hush (`hush box seal` to the machine's own key piped into `hush box open`). The CLIs never inherit `CORA_BOT_*`.
- `src/orchestrator.js` who answers and when: named agents answer alone and keep the conversation for follow-ups (`FOCUS_MS`), a mention of a non-agent wakes nobody, a human always gets an answer (a named agent that passes is asked again), a message naming nobody gets **exactly one** answer (chattiness decides who feels like speaking, the chattiest otherwise), `maxAgentTurns` stops agent-to-agent loops, only `settings.guildIds` are heard. A channel the main bot gets 403 on is private (`state.mainBlind`): only the agents whose own bot delivered a message from it (`state.heardFrom`, filled before the id dedup so every bot in the channel registers) may answer there, since only they can read or post. In a **thread** (a channel with a `parentId`) agents stay out unless summoned by name (`pickCandidates({summonedOnly})`). A **direct message** to an agent's own bot (`AgentBots` now connects each bot with DM intents and routes no-guild messages to `onDirectMessage`) is a private conversation that only that agent answers, even where it listens to no channel; it posts back with its own bot. Turns get `say` (post now), an inbox of messages written meanwhile (steering, delivered with tool results) and an automatic acknowledgement when a called agent stays silent — sent only after `ackQuietMs` (5 min) without a word from that agent in that channel (`spokeHereAt`), so a live conversation never fills with "ricevuto". A round frees its channel after `releaseAfterMs` (20 s) while agents on a task keep working in the background (`state.working`: they get new messages through the inbox, never a second turn). `resumeInterrupted()` picks up after a restart the computer tasks that were running (traces are saved every 30 s while they run).
- `src/brain.js` prompts and the tool loop; `elsewhere()` adds the agent's latest exchanges in its other places to every turn; `sleep()` is the nightly memory consolidation. The loop is the **Cora harness**: a task (a turn with the agent's computer, or a routine) runs until done (bounds 8 hours / 5000 steps). **Goal mode** (`settings.goalMode`, off by default): `Orchestrator.threadWork` admits one active task per thread, and that is the only lock: an agent is multi-threaded, one instance per thread with its own computer, goal and steering, as many threads at once as people talk to it in (there is no per-agent lock; `atWork` is gone). After a restart every interrupted thread resumes, not one per agent. `Brain.goalFor()` receives the addressed human request (including a queued `replyTo`) or a routine's current invocation. For chat approvals it also receives a bounded preceding transcript from that same channel to resolve references such as “ok, send”; it never imports memory, passive routine reports or later human requests as a new goal. `Brain.channelGoals` records that task's current condition. `Brain.activeTurns` exposes a serialized message-evaluation barrier to the orchestrator. A task addressed to another agent is evaluated semantically: an actual handoff stops the old worker without acknowledging the new request, releases both locks and schedules the named agent with its desktop; status and side conversations keep the worker. A stopped silent turn never enters the forced-PASS retry. Every provider uses Cora's verifier (no independent native `/goal`): it reads actual tool results, and can return blocked for future deadlines/access dependencies. A model evaluates incoming messages semantically (`Brain.evaluateMessage`): status questions get a recap while the same goal/worker continue; only actual task changes revise the goal, and explicit stop decisions abort execution. Tools wait for pending evaluations; CLI retries carry the updated goal, steering and prior results. Stop orders (including “stoppa tutto”), or a routine being paused/deleted/rescheduled, abort pending requests/CLIs and reject further tools. Interrupted stopped work and paused/deleted routines are not resumed. Without a goal the older reading applies: an agent that stops with nothing, with "shall I continue?" or with what it is about to do (`unfinished()`) is sent back to work, a finished one confirms once (`DONE`), the same tool call with the same arguments 4 times in 10 is a loop and is refused, long conversations are summarised by the agent (`COMPACT_CHARS`), a silent agent is reminded to send an update every 15 minutes. The same checks rerun Claude Code / Codex / Grok Build / Muse Code / Hermes when they stop early. Before either reading, an answer (or a `say`) that reports work as done (`claimsWork()`: "ho salvato", "l'ho creato", "salvato in memoria", "l'ho ricordato", "ho preso nota", "file salvato in /…", "I've sent", never a negated sentence) from a turn that called no tool beyond `say`/`notify`/`list_channels`/`ask_owner` and the lookups `list_routines`/`routine_history`/`recall`/`screenshot` is sent back once (a claim of checking, "ho controllato", is backed by any tool), with or without a task or a goal: every action, Hermes' included, goes through `runTool`, so no call means it did not happen. The agent must do it, check it with the tools if it means an earlier turn, or say it did not; a final answer that made the claim is not posted (a `say` has already gone out). Small local models make such claims often. `resumeTurn()` restarts a task cut short by a restart.
- **Progress review:** after 20 work-tool calls, the same semantic verifier examines actual recent results while the worker is still running. A demonstrated owner/access dependency redirects it to report completed results and `ask_owner`, rejecting further desktop searches/writes until a non-status owner message arrives. Memory, communication and own-routine tools remain available. A failed review permits work to continue; an incomplete goal alone does not stop useful work. Reviews use a 20-second bound and skip an obsolete goal after owner steering. Clarifications preserve the current goal; status questions preserve both it and the dependency.
- **Reminders and routine archive:** `routines` JSON adds immutable `kind` (`routine`/`reminder`), exact ISO `runAt`, archive timestamps and last verification. `routine_runs` is a persistent execution ledger with snapshots, results, trace/verification ids and a unique unfinished run per task. Reminders execute once when overdue and free; successful reminders are archived transactionally only after `Brain.verifyReminder()` gets an explicit positive verdict from the agent’s provider, including tool-free Claude/Codex subscription runs. Invalid/unavailable/contradictory verifiers fail closed. Failed/blocked reminders require manual retry or explicit rescheduling; busy ones defer. Stop/pause/archive/reschedule cancels stale work; restart recovery uses persisted trace evidence and respects offline stop orders. Soft deletion preserves archived definitions and execution history, including after agent removal. Existing routine traces/last results migrate once as unverified historical records. Authenticated `GET /api/routines/history` and `/api/routines/archive` accept agentId/kind/query/limit/offset. `set_reminder` and `routine_history` are always available through `OWN_TOOLS`; history is scoped to the calling agent. The agent’s Routine and reminders tab has Scheduled/Archive views; the Desk links to the global archive.
- `src/rooms.js` the panel's chat rooms (`web` salotto, `web-<agentId>` private); `src/traces.js` records each turn's reasoning (steps streamed over SSE, saved in the `traces` table).
- **Codex permission scope:** `runCodex()` supplies a short application contract through the official `developer_instructions` override. Its local host remains `-s read-only` with native shell/browser/editing tools disabled; exposed Cora MCP tools run separately on the agent desktop. Authorized connector writes use their actual schemas and permissions, while explicit owner read-only limits and real denials still apply. The goal verifier requires connector/tool/owner evidence for a write blocker instead of trusting an unsupported sandbox claim. No new endpoint, table, credential scope or sandbox grant is introduced.
- **Liveness guards:** visual loop detection compares screenshot contents and the preceding desktop action, not empty screenshot arguments. Computer/navigation calls include the last observed frame in their signature so the same coordinates on a changed page remain valid; genuinely repeated unchanged observations still stop. Goal verification must not require its own routine ledger to stop being `running` before the check returns, or require the final reply to be posted before normal turn completion. Discord delivery may recover from a personal bot’s 403 through the attributed shared bot only after successful history reads by both its own bot and the main bot in an allowed guild, never in private/DM scopes or after partial delivery. `Discord.say` reports `sentCount` on failure to prevent duplicate fallback.
- **Per-agent Discord access:** `AgentBots.canRead()` proves channel access through that agent’s own bot, even when the main listener can read the channel. Rounds filter candidates before selecting a speaker; inaccessible agents never acquire the desktop/thread lock. Cross-channel sends cannot fall back to main-bot read permission. New routine invocations are recorded blocked for denied channel access, and interrupted chat workers lacking access are marked stopped instead of resumed. Temporary failures remain distinct from a 403/404 denial. Routine locks and definition revisions are rechecked after the asynchronous permission lookup, so simultaneous due routines still admit only one worker. Agents without a configured personal bot retain shared-bot operation. The instance roster in the system prompt is explicitly not the current channel participant list.
- **Routine handoff and channel posting:** routine progress/results and cross-channel reports are passive archived messages; they never replenish conversation budget or schedule agent chatter. `messages.meta.passive` persists this behavior across history reloads. Passive messages remain explicitly marked in transcripts and in the dated, bounded context preceding an owner request: an owner's short mention can refer to another agent's collaboration request, while a passive report alone never authorizes a new task or revives a closed one. `state.humanQueue` retains fresh human messages across final delivery and wakes the conversation after locks release; `replyTo` identifies the human even when a routine report is now last. Disabled recipients and intentionally ignored messages cannot hold the queue; the agent chosen for a human message without names becomes the conversation focus. Semantic status/side-question replies acknowledge their message ids without restarting the worker. Every provider has `list_channels` and `say({text,channel_id})`, including agents without computers. Catalogs respect assignments, active transport and guilds, include own-bot channels, and cross-channel Discord delivery proves read permission. Do not require grog, shell access or new logins for Cora messaging. Successful direct delivery followed by PASS or an identical final reply does not post twice. Nor does a final reply that only notes the delivery (`deliveryNote()`: "Messaggio già in #general.", "Messaggio inviato.", "Fatto.") when the last tool was a `say` into this conversation: Grok Build, Muse Code and Codex end every run with a final message, and wrote one after answering with `say`. The `say` receipt for this conversation and the chat rules say the final reply is posted here anyway: write only what is new, or PASS.
- **doc in the Cora harness:** `src/doc.js` runs doc's own Python modules (`python3 -m doc.publish_guard|reply_check`, `PYTHONPATH` = the doc root from `findDoc()`) with doc's hook payloads, the instance's TypeSafe key as `TYPESAFE_API_KEY` and `DOC_USAGE_LOG=<home>/doc-usage.jsonl`; the rules stay in doc, never copied here. `runTool` asks it before a `shell` command that matches doc-hook's publishing prefilter (a `--body-file`/`-F`/`body=@`/`grog answer` file is read from the box and handed over as a heredoc, since doc runs on the host; unreadable means unchecked) and before `say`/`ask_owner`/`notify` (one stop per turn). `nextStep` checks the final reply once (`kind: "doc"`), before the claim and goal checks. Every failure, timeout or missing doc lets the action through. `Doc.activity()` reads the day's decisions from that log for the panel; `Doc.probe()` (`POST /api/doc/probe`) checks one exact rule and one Jev judgment with its log sent to /dev/null. The key is a panel key (`PUT /api/providers/typesafe/key` → hush `CORA_TYPESAFE_API_KEY`, live without a restart); `bin/run.sh` falls back to doc's own `TYPESAFE_API_KEY`. Claude Code runs with `--settings {"disableAllHooks":true}` so the owner's own hooks never run twice or wake on an agent's turn. Owner checks: `GET|PUT /api/doc/rules` lists doc's built-in Jev rules (`python3 -m doc.rules`) with their on/off state and the owner's own, validated by `cleanDocRule()` (key from the name, `on` ⊆ reply/comment, question ≤ 500, at most 20) and written whole to `<home>/doc-rules.json` (0600), which every doc run gets as `DOC_RULES`; `off` holds `reply:<key>`/`comment:<key>`, an own rule rests with `enabled: false`. `POST /api/doc/rules/test` tries a draft on every brain in use (`brainsInUse()`: distinct model, account and Ollama card of the enabled agents) through `src/rule-test.js`: the brain writes a text that breaks the rule, `doc.rules try` scores it (an example that breaks nothing is asked for once more, plainly, and marked `retried`), the brain gets doc's own stop message and rewrites, which is scored again; the job is polled at `/api/doc/rules/test/:id`, saves nothing, and needs the TypeSafe key. The panel's Controls tab unlocks Save only after a trial of the very draft. Tests use `fakeDoc()` (`test/helpers.js`).
- **Message evaluation** uses `settings.defaultModel` without tools and returns `status`, `update`, `stop` or `continue`. Evaluations are serialized; pending evaluations finish before another tool executes. A status reply reads actual tool results and the latest progress, sends one recap and keeps the same worker and goal. Do not replace this evaluation with keyword matching. The older `asksToStop()` helper is only a restart-recovery guard.
- **Cancellation** uses a turn-scoped `AbortController` through `LLM.chat`/`runAgent` into HTTP requests and subscription CLIs. Cancelled traces use the existing text status field with `stopped`; no database migration or new endpoint is required. A stop during a routine pauses that routine. Changing its `updatedAt`, disabling it or deleting it invalidates an active invocation, so an old worker cannot restore stale settings.
- `src/memory.js` retrieval (pinned + FTS5 relevance + recent). `src/store.js` is the only place that touches SQLite (`~/.cora/cora.db`).
- **Token accounting**: every provider hands back `usage {in, out}` (Ollama `prompt_eval_count`/`eval_count`, routers `usage.prompt_tokens`/`completion_tokens`, Claude Code the `result` event's usage with cache reads counted, Codex `turn.completed.usage`; Hermes reports none). `Trace.spent()` adds them up over the turn, `traces.tokens_in`/`tokens_out` keep them (added by migration, so old rows read zero), `Store.usageByDay()` folds them per agent per local day and `GET /api/usage` serves it to the panel's heatmap.
- **One task per agent and thread** (`Orchestrator.atWork` and `threadWork`): computer chat turns, routines and resumed tasks take both locks, so concurrent tasks never share an agent or thread; the routine records a `skipped` run with the reason. `Discord.post` prefixes `**Name** ·` only when its own username is not that name, since cora listens through an agent's own bot and would otherwise print the name twice.
- `src/llm.js` retries passing failures (`TRANSIENT`: capacity, rate limits, 5xx, dropped connections, timeouts, an empty answer) twice with growing waits. `chat()` always retries, since a model call has no side effects; `runAgent()` only while the run has executed no tool, so a retried turn never repeats side effects — the reason goes into the trace as a note.
- `src/llm.js` `contextLength(model, host)` asks `/api/show` what a model can hold and `chatOnce` sends it as `options.num_ctx` (capped at `MAX_CONTEXT`, 32k); `compactAt()` turns that into the character budget `src/brain.js` compacts against, instead of the old fixed `COMPACT_CHARS`. Without this Ollama truncates the oldest part of a long task without a word.
- `src/llm.js` `ollamaHostList()` is the machine's Ollama servers (`settings.ollamaHosts`, one per card) and `ollamaReport()` what each answers; `chat({ host })` sends an agent's turn to its own (`agent.ollamaHost`), since Ollama binds its cards at startup and never per request. `pullModel()` installs a model and follows the download; `POST /api/ollama/pull` runs it and reports through the panel's event stream.
- `src/orchestrator.js` `showWorking()` replaced the automatic "ricevuto": the typing indicator is refreshed for as long as the turn runs (7s on Discord, 4s on Telegram), and on Slack — which gives bots no indicator — the app adds 👀 to the message it took and removes it when it answers.
- `src/llm.js` `listModels()` marks each Ollama model `local` (a local Ollama also proxies the cloud ones, which carry `:cloud` or `remote`) and carries its `size`; `hardware()` answers `GET /api/hardware` (cached 10s in `src/web.js`) with the Ollama it talks to and its version, the models loaded right now (`/api/ps`: size and VRAM) and the cards from `graphicsCards()` (`nvidia-smi`, empty on a host without one). The panel's model list groups "Ollama su questa macchina" apart from Ollama Cloud, and the agent's profile shows the machine under the model. A model that is loaded reports what the card actually took (`residencyOf()` in `web/app.js`): Ollama leaves the rest on the processor, which costs most of the speed, so that measurement replaces the `fitOf()` estimate on its row.
- `src/llm.js` `providers().ollama` is true with `CORA_OLLAMA_API_KEY` **or** when `OLLAMA_URL` points at this machine or a private network (`LLM.localOllama`): an on-premise install talks to its own GPU, and `ollamaHeaders()` then sends no Authorization. Ollama Cloud still needs its key.
- `src/llm.js` providers: `claude/`, `codex/`, `grok/`, `muse/` and `hermes/` run CLIs (`src/cli.js`), which call cora's tools through `src/mcp-server.js` → `src/bridge.js`; `ollama/` (Ollama Cloud) and `orcarouter/` (OpenAI-format router, `routerChat()`, key `ORCAROUTER_API_KEY`) run on the Cora harness. Hermes runs one-shot with `-t cora` only (never its terminal, file or computer-use toolsets) and `--ignore-rules`, in Cora's own Hermes home whose `config.yaml` (`hermesConfig()`) takes the bridge session from `${CORA_BRIDGE_URL}`/`${CORA_BRIDGE_TOKEN}`; `bin/hermes-smoke.mjs` checks it live. No API-key providers for Claude/ChatGPT: the owner wants the subscriptions. argo-* models belong to another project and are never listed for Hermes. Model ids are `provider/model` with the provider in `MODEL_PROVIDERS` (`src/store.js`); the panel lets the owner type an id the list does not show. A Hermes model may name its endpoint first (`hermes/<router>/<model>`): `hermesEndpoint()` sends it to that router with its key, passed to Hermes as `${CORA_ENDPOINT_KEY}` so the key never lands in the generated config, in a Hermes home of its own (`<hermesHome>-<router>`) because parallel turns share one `config.yaml`; anything else runs on the Ollama of the agent's card (`ollamaHost`, in a home `<hermesHome>-<host>` of its own) or, without one, on Hermes' own endpoint, this machine's Ollama. Hermes refuses a model that holds less than 64K (`HERMES_MIN_CONTEXT`): the Hermes list marks one `usable: false`, each host's models carry `context`, the Cervello tab disables the row, and `runAgent` stops the turn before Hermes starts. Hermes from v0.22.3 runs `-z` through a shared gateway that starts the `cora` MCP server once, with the first turn's bridge token: later turns get 401 and could see another agent's tools. Install Hermes v0.21.x (or v0.22.2) where agents use it (`install.sh --skip-setup --commit <tag's commit>`). Only models that are really in the cloud get a Hermes cloud entry: a model installed here has no `name:cloud` twin. A local Ollama lists the cloud models it proxies whether or not the machine may run them: `ollamaReport()` asks `POST /api/me`, and a model that answers only after pairing is listed with `usable: false` and its reason. `providers()` therefore reports `ollamaLocal` (a server here) and `ollamaCloud` (an account, by key or pairing) apart, and the agent's **Cervello** tab is built on that pair: harness on the left, place (`local`/`cloud`) and models on the right, with `/api/state` carrying `ollamaCloud` (`signedIn`, `signinUrl`). `Subscriptions.start()` refuses a login whose CLI is not installed instead of ending in a failed device code, and `view()` carries `installed`.
- `src/tools.js` `OWN_TOOLS` (= `MEMORY_TOOLS` + `list_routines`/`set_routine`/`set_reminder`/`delete_routine`/`routine_history`) is what an agent may do about its own life without the computer; `MEMORY_TOOLS` keeps its older meanings (what does not count as work, what skips loop detection, what is not worth resuming). Agents working on cora's own code are told to use the clone at `~/GIT/@agents/cora` and never the owner's working tree.
- `src/tools.js` agent tools. Always: `say`, memory tools, `notify`, `ask_owner`, and the agent's own routines (`list_routines`, `set_routine`, `delete_routine`). Desktop tools require an owner-started task or a routine.
- `src/box.js` `browser(agentId, action, argument)` runs `cora-cdp` in the box and parses its JSON: the agent reads the page and its session from the same Chromium the owner watches (`box/cdp.mjs`, Node's own WebSocket, no dependency). Cookie and storage **values** are never returned, and the debugging port is bound to 127.0.0.1 inside the container. The browser is never launched by a driver and never gets `--enable-automation`, so pages do not see automation; `src/brain.js` counts `browser` among the visual calls, so reading a page again after something changed is work, not a loop.
- `src/box.js` docker CLI for the desktops (`cora-box-<agentId>`, volumes `cora-home-<agentId>` and `cora-sys-<agentId>` for Tailscale state and SSH host keys, noVNC on a random 127.0.0.1 port, sshd on the agent's fixed `sshPort`); outdated boxes are recreated when cora starts or from «Aggiorna».
- **Agent file delivery:** computer-authorized turns can call `share_file({path, agent})` to deliver an authorized file from their own `/home/agent/work` to another enabled agent with a desktop. `Boxes.shareFile()` reads at most 8 MB, rejects source escapes and destination symlinks, creates a private immutable copy in the recipient's `work/shared/<sourceId>/` directory and verifies SHA-256/bytes. Content-hashed names make retries idempotent without overwriting recipient changes. Payloads travel through Docker stdin, never chat or host temporary files; SSH and Tailscale are not required. The receipt exposes only recipient, path, hash and size. `send_file` remains the explicit channel attachment action.
- **Discord colleague mentions:** when posting an agent's message, explicit `@Name` and a leading `Name,`/`Name:` salutation resolve to that colleague's actual bot mention only if the bot can read the destination. Code snippets, email addresses and longer names are preserved. Ordinary references remain text, and passive messages remain passive. Telegram and panel messages keep their readable names.
- **Message delivery evidence:** `say` returns a Cora delivery receipt with the actual destination id/name, delivered message ids and real Discord mention ids. Goal verification treats a receipt for the current channel as delivery to that destination; it must not demand another cross-channel send or repeated notification merely because the channel was omitted in the tool arguments. Identical worker `say` calls within the same owner revision reuse one delivery, including concurrent calls; failed delivery can retry. Semantic status replies bypass that cache, and a real owner clarification permits a new delivery. Human-readable archived names remain separate from the delivered Discord markup. People are tagged too, not only agents: `Orchestrator.peopleFor()` maps the names of whoever wrote in this server's channels (the archive's `author_id`/`author_name`, `Store.people()`; the whole workspace on Slack) or was tagged there since the start (`knownPeople`, filled by `toItem()` and `slackText()`) to their user ids, and `tagPeople()` turns `@Name` outside code into `<@id>` on Discord and Slack alike. A name an agent also has, or that two people share, is never tagged, and neither is someone from another server. `toMrkdwn()` keeps `<@U…>` out of its escaping, or Slack would show the mention as text.
- **Routine completion:** goals receive the current local date/time and preserve the actions requested for this invocation. A planning/research/update routine must finish its presently feasible preparation and checks; it cannot become a queue-status report merely because a later verification is scheduled. Check-only routines still run one check, and future sends/publications remain scheduled rather than being awaited or anticipated.
- `src/subscriptions.js` selects official CLI identities per agent. **Resident subscriptions are enabled by default** (`settings.useResidentSubscriptions`): empty `agent.subscriptionId` selects the matching resident account, detected through official CLI account/status APIs. Metadata records tagged `resident` expose email, plan and status, never tokens; these accounts cannot be logged in, logged out or removed by panel routes. Resident mode uses the host's existing CLI credential context, with environment API keys/provider overrides stripped. The user explicitly restored this compatibility on 2026-10-26, superseding the earlier fresh-customer-only rule. Disabling resident mode blocks its use; an explicitly selected managed account never falls back to it. **Whose account:** a managed record keeps `connectedBy` (`{id, name}` of the panel user who created it or last started its login; resident records have none). The panel names every account as the viewer reads it ("Account del server", "Il tuo account", "Account di Sara"), tells a member when an agent runs on the server's account instead of theirs, and a new agent starts on an account its creator signed in themselves when one is ready (owner's request after a member connected ChatGPT on notseb and could not tell which account their agent used, 2026-10-31).
- **Subscription CLIs are one table:** `src/harnesses.js` (`HARNESSES`) gives each of Claude Code, Codex, Grok Build and Muse Code its label, the variable that moves its home (`homeVar`), its machine home and the only hosts a login may open. The store, `Subscriptions`, `LLM.runAgent` and the panel (`SUBSCRIPTION_HARNESSES`, `SUBSCRIPTION_ICONS`) read it instead of listing providers. Claude and Codex always get a resident account; Grok and Muse only where their CLI is installed (`Subscriptions.residentProviders()`), so instances without them show nothing new.
- **Grok Build** (`runGrok()`, `grok/`): Grok has no per-run MCP flag and keeps every session on disk (prompts, transcripts, `session_search.sqlite`) with no switch against it, so each turn runs in a Grok home of its own, `<cli-work>/<account>/grok-<id>`, deleted when the turn ends: its `config.toml` (`grokConfig()`) holds only the `cora` server with `${CORA_BRIDGE_URL}`/`${CORA_BRIDGE_TOKEN}`, and the login is read where it lives through `GROK_AUTH_PATH` (the account folder's `auth.json`, or `~/.grok/auth.json` for the machine), never copied. Turns on one account therefore run side by side. `models_cache.json` is copied to `<CORA_HOME>/grok-home` (`grokHome`) for the model list. `HOME` points at an empty folder inside that home and `GROK_{CLAUDE,CURSOR}_{AGENTS,HOOKS,MCPS,RULES,SKILLS}_ENABLED=0`: without them Grok loads the owner's `~/.claude.json` MCP servers and runs his Claude hooks. mise keeps its real folders (`miseFolders()`: `MISE_{CONFIG,DATA,STATE,CACHE}_DIR`), because on Omarchy `grok` is a mise wrapper (`mise x npm:@xai-official/grok -- grok`) that refuses to start under the empty HOME. `--tools search_tool,use_tool` is the only working restriction (`--tools ""` keeps every built-in): the model finds Cora's tools with `search_tool` (they count as "hidden tools") and calls them with `use_tool` as `cora__<name>`. Prompt in `--prompt-file`, Cora's system prompt in `--system-prompt-override`, `--output-format streaming-messages-json` (Claude Code's stream-json, read by the shared `messageStream()`), `--always-approve --no-memory --no-subagents --disable-web-search --no-auto-update`. Status: `grok models` ("You are logged in" / "You are not authenticated"); login `grok login --device-auth` (`accounts.x.ai/oauth2/device?user_code=`); models from `grokHome`'s `models_cache.json`, then the owner's, then a fixed list.
- **Muse Code** (`runMuse()`, `muse/`): `muse exec --json --preset empty` (no built-in tools), `--no-foreign-personal-context` (otherwise it loads the owner's Claude Code rules), `--disable-reminders --disable-request-user-input --disable-web-tools --no-session-log --approval-mode never`, and `--contributor-mode off` (Meta trains on a subscriber's turns by default). Cora's system prompt replaces Muse's with `-c run.system_prompt=` (input tokens 36K → 16K on a live turn) and the MCP server arrives for this run only with `-c mcpServers.cora=<json>` (a whole `mcpServers` map is refused), its env as `${VAR}`. Events are JSONL envelopes: `run.output.delta` text, `task.lifecycle.proposed` with `task_kind` `tool.<name>` marks a tool call, `run.usage`, `run.terminal.completed` with the answer. Accounts: `XDG_CONFIG_HOME` (login in `muse/auth.json`) and `XDG_DATA_HOME=<folder>/data`; `TBH_CREDENTIAL_BACKEND=file` always, because on a Mac Muse otherwise writes the login to the Keychain, which a service or ssh session cannot reach (`login succeeded but saving failed … keychain write failed (os status -61)`). Status `muse usage` (`Tier: …`, shown as the plan); login `muse login` (`auth.meta.com/oauth/device/?code=`). Models: `muse-wonder-1.0` (its default), `muse-spark-1.3`. `bin/cli-smoke.mjs grok|muse` runs one live turn on this machine's account with a probe tool and a forbidden `ls ~`.
- New managed accounts use private `$CORA_HOME/subscriptions/<id>` profiles (`CLAUDE_CONFIG_DIR` / `CODEX_HOME` / `GROK_HOME` / `XDG_CONFIG_HOME`), stripped credential/provider overrides and separate working folders; official CLIs own tokens and renewal. Codex uses app-server device-code login; Grok and Muse print a page and a code (`DEVICE_LOGIN`), which the panel shows like Codex's and the owner confirms on the provider's page; Claude uses official `auth login` and transient code submission. Authorization happens in the panel user's browser. Claude must confirm its managed profile directory (`auth status --json`, CLI >=2.1.268). Turns sharing an account run side by side (`Subscriptions.running` counts them); only a login, check or removal of that account waits for them, and a cancelled turn stops at once. Each Grok turn has its own Grok home under the account's work folder, deleted when it ends, so parallel turns never share Grok's on-disk sessions. Auth URLs/codes stay out of SQLite/activity/SSE. Assigned accounts cannot be removed; deleting an unused managed account logs out and removes only its isolated profile.
- **Connections API:** `GET/POST /api/subscriptions`, `GET/DELETE /api/subscriptions/:id`, `POST /api/subscriptions/:id/{login,code,cancel,check}`, and `POST /api/subscriptions/resident/check`. `PUT /api/providers/{ollama,orcarouter}/key` persists a panel-submitted key through `storeSecret`/hush before updating the live provider; the key never enters SQLite, responses or activity. Existing panel auth and CSRF apply. Settings has Connections, Channels, Agents, Preferences and Access tabs; hidden panes remain mounted to preserve unsaved form values. Connections centralizes resident discovery, remote account onboarding and API keys, and the agent form uses the same progressive account picker.
- `src/push.js` Web Push (VAPID + aes128gcm) to the owner's devices; agents' `notify` tool and panel requests. `ask_owner` posts where the conversation is (`Orchestrator.askOwner`): a Discord/Telegram channel (owner mentioned, answers as text, no Web Push) or a panel room (buttons + push); the owner's next message there is routed to the asking agent (`state.request` in `address()`).
- `src/web.js` panel API, SSE, password login (HMAC cookie, `X-Cora` header + Origin check on writes), authenticated noVNC proxy at `/box/<agentId>/`.
- **Instance access:** `panel_users`, `panel_sessions` (SHA-256 token hashes), `access_domains`, `access_emails` and `access_audit` in the instance SQLite database track separate identities, first/last activity and safe action categories. `GET/PUT /api/access` and `PUT /api/access/users/:id` are owner-only. Other operational features have the same permissions for owner and admitted members. Domain admission requires a verified email and an exact domain or individually authorized address; owner access is independent of the allowlist. Revocation invalidates sessions and closes SSE/WebSocket connections; the panel handles `access-revoked` explicitly. Panel messages carry the authenticated user's id/name, never an actor supplied in the request body. Legacy pre-membership owner cookies and emergency links remain owner access.
- **Cloud membership:** `identities.email_verified` and `space_members(slug,account_id,last_entered)` track verified identity claims and accessible spaces. Non-owner `/go/:space` requests first send a short-lived signed pass to the target instance's `POST /api/cloud/access` (audience `access:<space>.<domain>`); the instance evaluates its own policy. The actual sign-in pass is separately signed for that instance and rechecked there. Members keep separate cloud accounts, never the owner's account. Verified email claims use the latest identity; owner identity display retains the account email. New individual Cora sessions persist across restarts.
- **Context:** `src/context.js` supplies authenticated `GET /api/context` from a fixed inventory of Markdown instruction files and shared memory. The preview of owner instructions is exactly `Brain.ownerInstructions()` (60,000 characters). Resident and existing managed profile notes expose their provenance; Codex local notes are explicitly excluded because Cora invokes it with `--ignore-rules`, and Claude files are marked available without claiming per-turn loading. Missing files are explicit; arbitrary requested paths and symlinks resolving to non-Markdown files are never read. The main `#/contesto` navigation provides source selection, read-only text, copy and refresh on desktop and mobile.
- **Database context files:** `context_documents` stores name/content, enabled state, revision, timestamps and author ids. Authenticated `POST /api/context/documents` and `PUT/DELETE /api/context/documents/:id` use the normal CSRF boundary and `context` activity category; all admitted users have the same operational permissions. Text imports accept UTF-8 Markdown/TXT; limits are 20 documents, 30,000 characters per document and 60,000 active characters in total. Updates may include `expectedRevision` and reject stale writes with 409. Enabled documents are injected in `Brain.systemPrompt()` for every provider from the next turn, independently of subscription source. Context lists DB documents with create/upload/edit/enable/delete controls; native server files remain read-only. The landing's harness section includes a short shared-context note.
- `web/` vanilla JS panel, no build. `box/` the desktop image (Debian, XFCE, Chromium, x11vnc, noVNC; `autocutsel` keeps X's PRIMARY and CLIPBOARD selections in step both ways, without which copy and paste through noVNC silently does nothing) — plus the tools every agent gets: `hush` (pinned by release tag, `ARG HUSH_VERSION`) to use a secret by name without seeing it, and `ambox` (pinned by npm version) for its own end-to-end encrypted mailbox; the same `RUN` checks both start, so a bad install fails the build.
- `src/pass.js` passes from usecora.space: Ed25519 key derived from `CORA_CLOUD_SEED`, `signPass`/`verifyPass` (audience = the space's host, one minute, single use). `src/web.js` turns a pass (`/auth/cloud`) or a one-time link made on the host (`/auth/link`, `bin/login-link.mjs`) into the panel session; with `CORA_CLOUD_URL`/`KEY`/`SPACE` set the password login is off. With only `CORA_CLOUD_KEY` (set in the installation's non-secret `~/.cora/env`, read by `bin/run.sh`), `POST /api/cloud/notice` accepts notices signed by the cloud (audience `notices`, e.g. a waitlist sign-up) and posts them as "Cora" in the Discord channel named in `settings.noticeChannel` (default `waitlist`); the cloud sends them to the space named in `CORA_CLOUD_NOTIFY`.
- `cloud/` usecora.space: `src/app.js` routes by Host (apex = landing + sign-in, `<space>.<domain>` = proxy to that space's Cora), `src/oauth.js` Google/GitHub with PKCE, `src/store.js` accounts, identities, invites, spaces, requests, waitlist (`~/.cora-cloud/cloud.db`), `src/views.js` the pages (English only; the landing has no sign-in links until sign-in opens, `POST /waitlist` takes an email and a company), `web/` their CSS/JS, `cli.js` adds spaces by hand and lists the waitlist. Tests in `test/cloud.test.js`.

## Rules

- Secrets only through hush (`bin/run.sh`). Discord: cora listens through an agent's own bot with the Message Content intent, or an optional dedicated `CORA_DISCORD_LISTENER_TOKEN`; it never borrows another tool's bot. Telegram: `CORA_TELEGRAM_BOT_TOKEN` and `CORA_TG_BOT_<NAME>`, stored from the panel through `src/secrets.js`. Bot API URLs carry the token: never log them.
- The agents are not tied to a platform (the owner asked): prompts say where they are right now, never that they "live on Discord".
- Bots can be in servers the agents must not hear: only `settings.guildIds` are heard, keep everything else out of it.
- No runtime dependencies; add any through the mcaifee gate.
- The CLIs must never get tools that act on the host: Claude runs with `--tools ""`, Grok with `--tools search_tool,use_tool`, Muse with `--preset empty`, Codex with `-s read-only` and shell/unified_exec/browser/computer-use/multi_agent disabled (its code mode stays on because MCP calls go through it; verified it cannot read host files). Re-verify with a live probe after CLI upgrades.
- Agents get the owner's `~/.agents/AGENTS.md` in their system prompt (the owner asked for it explicitly). Do not strip it.
- Every behaviour change needs an integration test in `test/cora.test.js` (stand-in Discord, Ollama and docker in `test/helpers.js`).
- UI copy is written in Italian and translated through `web/i18n.js` (English); content written by people or agents is wrapped in `raw()` and never translated. Code, comments and docs are English.

## Deployment

usecora.space runs on the host behind the grog relay (`~/.grog/sites.json`: the apex and each space name point at the cloud's port 4380) with `cloud/bin/start.sh`; each space's Cora gets `CORA_CLOUD_URL=https://usecora.space`, `CORA_CLOUD_KEY` and `CORA_CLOUD_SPACE`.

Runs on a macOS host as the LaunchAgent `org.turinglabs.cora` from `~/Services/cora`, listening on 127.0.0.1:4370; put it behind your own HTTPS tunnel or reverse proxy. Deploy with `CORA_DEPLOY_HOST=user@host deploy/macos.sh` (it rebuilds the desktop image only when `box/` changed).

Both deploy scripts take `--skip-box` (leave the desktop image alone), `--build-box` (build it there anyway) and `--ship-box` (build it here and `docker save | docker load` it over, refusing when the two machines' architectures differ). A code change must never cost the customer's machine an image build: that is what `--skip-box` is for.

**On-premise (`deploy/linux.sh`, `deploy/cora.service`, `deploy/ON-PREM.md`):** an install on the customer's own Linux machine, under an ordinary user: systemd user service with lingering, Node ≥22.13 found and recorded as `CORA_NODE`, the customer's own hush vault for every secret, their docker for the desktops, and no root anywhere. It is published through a tunnel (cloudflared as a user process, no inbound port) or their own reverse proxy. `CORA_PUBLIC_HOST` is the domain it answers on, and the cloud's passes are signed for that host; a cloud space created with `--public <https url>` sends people straight there instead of proxying them, so customer traffic never crosses usecora.space.
